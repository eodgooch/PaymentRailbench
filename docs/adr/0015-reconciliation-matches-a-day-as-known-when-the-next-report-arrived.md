# Reconciliation matches a Banking Day as the Ledger knew it when the next day's report arrived, and a Break stays open until a person resolves it

Reconciliation is two-way, per Provider per Banking Day D (`railbench.reconciliation`): the Payments behind the Provider's Clearing Accounts, as the Ledger recorded them, against the lines of the Settlement Reports it ingested (ADR 0014). It waits for two reports, D's and the next Banking Day N's, and matches what the Ledger knew at the moment the later of the two was received (`known_at`): every Payment, state change, Inbox outcome, report and Provider Adjustment decision it reads is filtered to a Recorded Time (or receipt) at or before that moment. Every one of those tables is append-only, so a day's view never changes, and matching it is a pure function (`matching.match`) with its inputs and outputs in a fixed order; re-running a day, however late, finds the same Breaks and adds nothing. We wait for N's report so a line one Banking Day late reads as a timing mismatch rather than missing at the Provider, which we couldn't tell apart on D's report alone; we rejected raising a provisional Break and reclassifying it later, since that edits what the Exception Queue said, and rejected matching "as known now", which would make a re-run depend on when it ran. A settled Payment is expected on the report of the Banking Day its Settlement Effective Time counts toward under the Provider's published Cutoff rule (`report_day`, the same function the Simulator uses), and a line names its Payment by the Provider's Payment ID, cross-checked against the Idempotency Key, Rail, direction and currency; a Payment's line is its first agreeing settlement line, by report day then position. One rule per Break Type: **missing at Provider**, a Payment settled for D's report with no line on any report up to N's; **timing mismatch**, its line on another report than D's (raised on D's run when the line is on a report up to N's, otherwise on the run of the report it's on, after D's run has already found it missing); **amount mismatch**, its line's amount isn't what settled (+ a pull, - a push), raised with the timing rule's run; **duplicate**, a second settlement line for one Payment (on the report it's on), or a re-issue of D's report (kept as a `conflict` by the ingest, received by `known_at`) stating other lines, one Break per currency, exposing the money it states differently; **status mismatch**, a settlement line for a Payment the Ledger hadn't recorded settled (in flight, declined or canceled), or a Provider Adjustment still `pending`; **missing in Ledger**, a line naming no Payment the Ledger has, or one contradicting the Payment it names, or a Provider Adjustment the Ledger left `unmatched` (SPEC §4.5's "Reconciliation flags it"). A booked Provider Adjustment agrees with the Ledger and is no Break. A malformed report is no Break: there is nothing to match, and the day waits for a readable one. A Return isn't on a report (ADR 0014) and a return exception isn't a Break (ADR 0013), so Reconciliation doesn't repeat it; ADRs 0012 and 0013 left raising return exceptions and Payouts waiting on unfunded buyers "in the Exception Queue" to this ticket, and we keep the Queue to Breaks, as the glossary defines it, leaving those to be listed beside it (`GET /return-exceptions`, and the MCP server and nightly report, #11). A run is one database transaction under a lock on (Provider, day), appended once per (Provider, day) with the reports it read, its `known_at` and its Actor, the `reconciliation@1.0.0` system job, which runs on the Ledger's Clock after report ingest and reconciles every day whose two reports are in. A Break's id is a hash of (Provider, day, Break Type, match key), the match key being the Provider's Payment ID for a Payment's Break and the line ID (or `report:<SHA-256>:<currency>`) for a line's, so the same disagreement is the same Break in every fresh database; it stores its exposure (non-negative Minor Units in one currency: the money in question, the difference for an amount mismatch), its facts (expected and reported day, amount and state, in words too) and its evidence as rows in `break_evidence`, each a foreign key to exactly one Payment, state change, Inbox event, Ledger Transaction, report, report line or Provider Adjustment decision, so a `SELECT`-only reader (the MCP server's `explain_break`, #11) can follow it without parsing anything. Age isn't stored: it's derived from the Break's detection, at the run's Recorded Time, to now or to its resolution. Nothing resolves a Break on its own, not even a later run that no longer finds the disagreement: the Exception Queue is the open Breaks, largest exposure first, then oldest, then by id, and a person resolves one, once, with an operator ID (and the approved Proposal ID when acting on one, #16) and exactly one of a correcting Transaction already in the Ledger, posted through the Journal by deterministic code, or a reason (checked in code and by the database); a system job never resolves one, so no model output ever closes a Break (ADR 0001). Daily Close (#10) asks `day_status`, or `GET /reconciliations/{provider}/{date}`, whether the day was reconciled and how many Breaks are open with what exposure. A Scenario run goes on to the report after its last day with anything on it, so every such day is reconciled, and replaying the Ledger reruns the job at each moment it recorded a run, reproducing the Breaks exactly; resolutions are a person's acts, like Transactions posted through the API, and aren't replayed. Reconciliation never reads the Fault Manifest (it may not import `railbench.scenarios`, and the app role can't read the `simulator` schema): the tests compare its Breaks with the manifest, never the code. In a running service on the wall clock, a write that commits after a run with a Recorded Time before its `known_at` is missed by that run and added by a re-run; Scenario runs, on one ManualClock, can't produce one.

What each Fault becomes:

| Fault (ticket) | Break |
|---|---|
| duplicate delivery (05) | none: the Inbox applies the event once |
| out-of-order delivery (05) | none: the state machine advances or records the late event stale or as an exception |
| delayed delivery (05) | none if the event lands by `known_at`; a settlement still unheard then is a status mismatch on its day |
| Late Return (07) | none: a return exception, not a Break |
| missing report line (08) | missing at Provider |
| wrong report amount (08) | amount mismatch |
| settlement after Cutoff (08) | timing mismatch, on the day it should have counted toward |
| Provider Adjustment (08) | none once booked; status mismatch if still pending at `known_at` |
| orphan adjustment (08) | missing in Ledger |
