# Reconciliation matches a Banking Day as the Ledger knew it when the next day's report arrived, and a Break stays open until a person resolves it

Reconciliation is two-way, per Provider per Banking Day D (`railbench.reconciliation`): the Payments behind the Provider's Clearing Accounts, as the Ledger recorded them, against the lines of the Settlement Reports it ingested (ADR 0014). It waits for two reports, D's and the next Banking Day N's, and matches what the Ledger knew at the moment the later of the two was received (`known_at`): every Payment, state change, Inbox outcome, report and Provider Adjustment decision it reads is filtered to a Recorded Time (or receipt) at or before that moment. Every one of those tables is append-only, so a day's view doesn't change once its writes have committed, and matching it is a pure function (`matching.match`) with its inputs and outputs in a fixed order. We wait for N's report so a line one Banking Day late reads as a timing mismatch rather than missing at the Provider, which D's report alone can't tell apart; we rejected raising a provisional Break and reclassifying it later, since that edits what the Exception Queue said, and rejected matching "as known now", which would make a re-run depend on when it ran. A settled Payment is expected on the report of the Banking Day its Settlement Effective Time counts toward under the Provider's published Cutoff rule (`report_day`, the same function the Simulator uses), and a line names its Payment by the Provider's Payment ID, cross-checked against the Idempotency Key, Rail, direction and currency; a Payment's line is its first agreeing settlement line, by report day then position. One rule per Break Type, each its own function: **missing at Provider**, a Payment settled for D's report with no line on any report up to N's; **timing mismatch**, its line on another report than its expected day's; **amount mismatch**, its line's amount isn't what settled (+ a pull, - a push); **duplicate**, a second settlement line for one Payment (on the report it's on), or a re-issue of D's report (kept as a `conflict` by the ingest, received by `known_at`) stating other lines, one Break per currency, exposing the money it states differently and listing the differing lines of both versions in its facts, so nobody has to re-read the raw re-issue; **status mismatch**, a settlement line for a Payment the Ledger hadn't recorded settled (in flight, declined or canceled), or a Provider Adjustment still `pending`; **missing in Ledger**, a line naming no Payment the Ledger has, or one contradicting the Payment it names, or a Provider Adjustment the Ledger left `unmatched` (SPEC §4.5's "Reconciliation flags it"). A Payment's timing and amount are judged on its expected day's run when its line is on a report up to N's. A line later than that is judged on the run of the report it's on, after the expected day's run already found it missing at the Provider. So one cause gives two Breaks: the later one names the earlier in `facts.related_breaks` (its id is computable from provider, day, type and match key), both have the Payment in their evidence, and `GET /breaks/{id}` shows the link from either end. The triage agent (#16) should cluster on `related_breaks`. A booked Provider Adjustment agrees with the Ledger and is no Break. A malformed report is no Break: there is nothing to match, and the day waits for a readable one. A Return isn't on a report (ADR 0014) and a return exception isn't a Break (ADR 0013), so Reconciliation doesn't repeat it. ADRs 0012 and 0013 left raising return exceptions and Payouts waiting on unfunded buyers "in the Exception Queue" to this ticket; we keep the Queue to Breaks, as the glossary defines it: return exceptions are listed beside it (`GET /return-exceptions`, and the MCP server's tools, #11), and waiting Payouts surface through the MCP server's tools (#11) for the triage agent (#16). A settlement whose webhook is still unheard at `known_at` is a status mismatch and stays open, counted by Daily Close's threshold (#10), even after the webhook lands and nothing disagrees any more: that is intended, since a person confirms the late webhook landed and resolves it. A run is one database transaction under a lock on (Provider, day), appended once per (Provider, day) with the reports it read, its `known_at` and its Actor, the `reconciliation@1.0.0` system job, which runs on the Ledger's Clock after report ingest and reconciles every day that's ready. A Break's id is a hash of (Provider, day, Break Type, match key), the match key being the Provider's Payment ID for a Payment's Break and the line ID (or `report:<SHA-256>:<currency>`) for a line's, so the same disagreement is the same Break in every fresh database. It stores its exposure (non-negative Minor Units in one currency: the money in question, the difference for an amount mismatch), its facts (expected and reported day, amount and state, in words too), when it was detected (the run's Recorded Time), and its evidence as rows in `break_evidence`, each a foreign key to exactly one Payment, state change, Inbox event, Ledger Transaction, report, report line or Provider Adjustment decision, so a `SELECT`-only reader (the MCP server's `explain_break`, #11) can follow it without parsing anything. Age isn't stored: it counts from when D's report was due (20:00 New York on D) to now, or to the Break's resolution, so the Breaks of one run rank by the Banking Day they concern rather than tying on their detection. The Exception Queue is the open Breaks, ordered within each currency by exposure (largest first), then age (oldest first), then id; currencies come in code order, because comparing exposures across currencies means nothing, and until USDC (M4) there is only one. Nothing resolves a Break on its own, not even a later run that no longer finds the disagreement. A person resolves one, once, with exactly one of a correcting Transaction already in the Ledger (posted through the Journal by deterministic code) or a reason, checked in code and by the database. The **Resolver** is a person: an operator ID, plus the approved Proposal ID when the resolution came from one (#16). It isn't an Entry's person Actor, which needs both, because resolving a Break moves no money and a person may close one by their own judgement with a reason; a correcting Transaction carries its own Actor. A system job never resolves one, so no model output ever closes a Break (ADR 0001). Daily Close (#10) asks `day_status`, or `GET /reconciliations/{provider}/{date}`, whether the day was reconciled and how many Breaks are open with what exposure. A Scenario run goes on to the report after its last day with anything on it, so every such day is reconciled, and replaying the Ledger reruns the job at each moment it recorded a run, reproducing the Breaks exactly; resolutions are a person's acts, like Transactions posted through the API, and aren't replayed. Reconciliation reads reports only through a `ReportReader` (a Provider's name and how it reads its reports) and never reads the Fault Manifest (it may not import `railbench.scenarios`, and the app role can't read the `simulator` schema): the tests compare its Breaks with the manifest, never the code. On a Scenario's ManualClock every write commits before the next tick, so a re-run of a day always finds exactly the same Breaks. On the wall clock a write can read the Clock before `known_at` and commit after a run has read, so the job, the API and `make reconcile` wait `RECONCILIATION_SETTLE_SECONDS` (default 300; 0 in a Scenario run) past `known_at` before reconciling a day. That narrows the gap without closing it: a write slower than the margin is missed by the run and added by a re-run, never the other way round.

What each Fault becomes. The issue names the Faults of tickets 05 and 08; `duplicate_report_line` is a Settlement Report Fault added here in ticket 08's style, so that some Fault produces every Break Type:

| Fault (ticket) | Break |
|---|---|
| duplicate delivery (05) | none: the Inbox applies the event once |
| out-of-order delivery (05) | none: the state machine advances, or records the late event as stale or as an exception |
| delayed delivery (05) | none if the event lands by `known_at`; a settlement still unheard then is a status mismatch on its day |
| Late Return (07) | none: a return exception, not a Break |
| missing report line (08) | missing at Provider |
| wrong report amount (08) | amount mismatch |
| settlement after Cutoff (08) | timing mismatch, on the day it should have counted toward |
| duplicate report line (09) | duplicate, on the report it's listed twice on |
| Provider Adjustment (08) | none once booked; status mismatch if still pending at `known_at` |
| orphan adjustment (08) | missing in Ledger |
