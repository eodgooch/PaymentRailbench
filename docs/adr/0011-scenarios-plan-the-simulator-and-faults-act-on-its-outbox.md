# Scenarios plan the Simulator, Faults act on its outbox, and the manifest stays on the Simulator's side

A Scenario is a YAML file parsed into strict Pydantic models (`railbench.scenarios.model`): Customers, ACH pulls with an amount in Minor Units and an ending (settle, decline or cancel), named Faults, and optionally random Faults at a rate. All randomness is drawn up front from one `random.Random(seed)` in a fixed order (Payments as listed, events as emitted) and resolved into a concrete plan per Payment, which the runner hands the Simulator before the Ledger originates the Payment; the Simulator itself makes no random choices and reads no Clock but the shared ManualClock, and its Payment IDs and event IDs are hashes of the Payment's Idempotency Key (and the event type) rather than database sequences, so the same Scenario and seed give the same IDs, delivery order, Clock times, Fault Manifest and Ledger in every fresh database. (Amended by ADR 0014: this once held whatever else the database held, but a Settlement Report covers every Payment its Provider settled that day and is frozen once published, so a second run in one database would find its days' reports published without its settlements; the runner now refuses a database that isn't fresh.) The one wall-time dependency left is the webhook HTTP timeout: in a Scenario run it is a generous 60 s, and any failed or timed-out delivery fails the run instead of being retried, because a retry would move the run off its seed. Faults are a discriminated union on `kind`, shared by the Scenario file and the Simulator, so a new kind (Returns, Cutoff and Settlement Report Faults, #7 and #8) is one more variant in that union plus one injection case in the Simulator. Delivery Faults act on the Simulator's outbox when an event is emitted, and go out over the normal signed webhook path: a duplicate adds delivery rows with the same event ID and body, a delay pushes the first attempt out on the Clock, and an out-of-order Fault holds an event until a named later event of the same Payment has been delivered (we rejected expressing it as a delay, because whether it really arrives second would then depend on how the run ticks). Each injected Fault is written to `simulator.faults` with a cause code and its true root cause in words, and every run writes that out as the JSON Fault Manifest (`reports/manifests/<scenario>-<seed>.json` by default); the Ledger can't read it, because its database role has no access to the `simulator` schema and the `ledger` and `payments` packages may not import `railbench.scenarios` (both tested). A planned decline or cancellation happens at the time the Payment would have settled. Out-of-order delivery means a `submitted` can arrive after its Payment's decline. `decide()` treats it as stale only if the Ledger recorded the Payment as submitted before it ended; if the Payment went straight from created to declined or canceled, a `submitted` now may mean the Provider really sent the debit, so it stays an impossible transition: an exception record and no Ledger write. The runner moves the ManualClock straight to the next moment anything is due instead of ticking at a fixed step, so runs are quick and their tick times are part of the deterministic output. Replaying the Inbox reads everything it needs from the source database alone and feeds the same inputs into an empty one: Accounts and Payments as recorded, each Inbox body at the time it was first received, and the availability job at each moment it recorded doing something (the Recorded Times of the `available` state changes it appended). A job run that released nothing wrote nothing and would release nothing on replay, so those moments are all a replay needs, and we didn't add a table of job runs; because the Ledger reads time only from its Clock, Recorded Times come out the same as well, so the comparison is exact on everything but surrogate IDs: Transactions, Settlements, Holds and Hold ends by Idempotency Key, with amounts, Accounts, Effective and Recorded Times and Actors (a Provider Event Actor named by its Provider event ID), and Payments with their state changes and Inbox outcomes. An event the Ledger first stored with no outcome (its Payment not yet recorded) and applied on a later redelivery would replay at its first receipt, a case Scenario runs never produce. The runner plans the Simulator in-process; a control endpoint for a Simulator in another process is left to `make night`.
