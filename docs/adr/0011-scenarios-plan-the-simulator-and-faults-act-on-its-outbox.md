# Scenarios plan the Simulator, Faults act on its outbox, and the manifest stays on the Simulator's side

A Scenario is a YAML file parsed into strict Pydantic models (`railbench.scenarios.model`): Customers, ACH pulls with an amount in Minor Units and an ending (settle, decline or cancel), named Faults, and optionally random Faults at a rate. All randomness is drawn up front from one `random.Random(seed)` in a fixed order (Payments as listed, events as emitted) and resolved into a concrete plan per Payment, which the runner hands the Simulator before the Ledger originates the Payment; the Simulator itself makes no random choices and reads no wall clock, and its event IDs are a hash of the Payment's Idempotency Key and the event type rather than a sequence, so the same Scenario and seed give the same event IDs, delivery order, Clock times, fault manifest and Ledger. Faults are a discriminated union on `kind`, shared by the Scenario file and the Simulator, so Returns, Cutoff and Settlement Report Faults (#7, #8) join as new kinds. Delivery Faults act on the Simulator's outbox when an event is emitted, and go out over the normal signed webhook path: a duplicate adds delivery rows with the same event ID and body, a delay pushes the first attempt out on the Clock, and an out-of-order Fault holds an event until a named later event of the same Payment has been delivered (we rejected expressing it as a delay, because whether it really arrives second would then depend on how the run ticks). Each injected Fault is written to `simulator.faults` with a cause code and its true root cause in words, and the runner writes that out as the JSON fault manifest; the Ledger can't read it, because its database role has no access to the `simulator` schema and the `ledger` and `payments` packages may not import `railbench.scenarios` (both tested). A planned decline or cancellation happens at the time the Payment would have settled. Out-of-order delivery means a `submitted` can arrive after its Payment's decline, so `decide()` now treats it as stale (created and submitted were passed on the way) rather than an exception. The runner moves the ManualClock straight to the next moment anything is due instead of ticking at a fixed step, so runs are quick and their tick times are part of the deterministic output. Replaying the Inbox feeds the same inputs (Accounts and Payments as recorded, each Inbox body at the time it was first received, and the availability job at each original tick) into an empty database; because the Ledger reads time only from its Clock, Recorded Times come out the same as well, so the comparison is exact on everything but surrogate IDs: Transactions, Settlements, Holds and Hold ends by Idempotency Key, with amounts, Accounts, Effective and Recorded Times and Actors (a Provider Event Actor named by its Provider event ID), and Payments with their state changes and Inbox outcomes. An event the Ledger first stored with no outcome (its Payment not yet recorded) and applied on a later redelivery would replay at its first receipt, a case Scenario runs never produce. The runner plans the Simulator in-process; a control endpoint for a Simulator in another process is left to `make night`.
