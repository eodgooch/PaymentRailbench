# Provider Events are verified, stored raw, then applied once, and the Ledger decides when ACH funds are Available

A webhook is verified first: HMAC-SHA256 under `WEBHOOK_SIGNING_SECRET` over `"<unix seconds>.<raw body>"`, sent as `Railbench-Signature: t=…,v1=…`, compared in constant time, and refused (401, logged, stored nowhere) when it doesn't match or its timestamp is more than 5 minutes from the Ledger's Clock. The sender signs each retry afresh. A verified event goes into the Inbox raw (body bytes and headers), unique by (Provider, event ID), so a redelivery is recognised before anything is applied, and it's applied at most once: under an advisory lock on the Payment, only while its Inbox row has no outcome, recording exactly one of `applied`, `stale` or `exception`. An event for a Payment the Ledger hasn't recorded yet is kept in the Inbox, gets no outcome, and is answered 503 so the Provider redelivers it. Payments, the Inbox, outcomes and state changes are append-only like the Ledger: the current state is the furthest state appended, at most one row per (Payment, state), never an updated status column, so replaying the Inbox in order reproduces the Ledger (tested). An ACH pull is booked entirely through the Journal with the Provider Event as Actor: a pending Transaction (Clearing Account debit, Customer Balance credit) at `submitted`. At `settled`, the Ledger appends a Settlement of that Transaction, posts a Transaction moving the money from the Clearing Account to Bank Cash (so Clearing nets to zero), and places a Hold on the Customer Balance for the amount. A decline or cancellation before settlement is a pending Reversal. Applying one event is one database transaction: the Journal runs as a unit of work on the Inbox's connection, so its writes, the state changes and the outcome commit together, and a step the Ledger refuses rolls back (a savepoint) to leave only the exception. The Provider never says when money is Available. The Ledger releases the Hold, as a system job on its own Clock, at midnight New York time at the start of the second Banking Day after the Banking Day the money settled on, which is when the R01–R03 Return Window closes (ADR 0004). We chose a Hold over teaching the balance query about ACH, because Holds already reduce Available, bitemporally, and the release names its Actor. Banking Days follow the Federal Reserve's published schedule: weekends off, a Sunday holiday observed on the Monday, and a Saturday holiday not observed, since the Reserve Banks open the Friday before. The Simulator submits an ACH pull when it's created, counts it toward the next Banking Day if it's after its 16:00 New York Cutoff, and settles it at 08:30 New York time on the Banking Day after that. In tests both services run in-process on one ManualClock, talking over real HTTP. Running services use the wall clock, and a shared clock for demos is left to `make night`. SPEC §1 asks for no queues. The Simulator's `events` table is in effect a small delivery outbox, and both services run a background ticker thread. We accept both because a Provider has to retry webhooks and the Ledger has to act on its Clock. Each is a table or a loop inside a service we already run, not a broker, and tests drive both by hand. The Simulator claims due events in a short commit and POSTs outside any transaction, so a slow Ledger holds no locks.
